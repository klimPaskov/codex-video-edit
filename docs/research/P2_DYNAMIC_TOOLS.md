# P2 host-defined tool boundary probe

Checked 2026-09-20 against the pinned official Codex 0.155.1 App Server and its generated protocol. [`thread/start.dynamicTools`](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/app-server-protocol/src/protocol/v2/thread.rs) is experimental and requires `initialize.capabilities.experimentalApi`. The pinned [App Server dynamic-tool handler](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/app-server/src/dynamic_tools.rs) sends `item/tool/call` to the host. This is a possible way to expose guarded editor tools without configuring an MCP server, whose resource helpers remain a P2-07 concern. It is not yet the product transport.

The ignored isolated Linux guest test runs the packaged official binary over stdio with no MCP server, a private app-owned ChatGPT credential copy, and a fresh context. It reads the live model catalog and requires `gpt-5.6-luna` with `high`. A namespaced host-defined read-only tool then receives exactly one `item/tool/call`; the bounded main-side callback validates its bare tool name, active thread and arguments. One actual code-mode `exec` cell computed `ALL_TOOLS.map(item => item.name)` and passed the resulting array to that host tool. The array contained only `codex_video_edit__editor_probe`. A private correlated rollout audit verified that exact code cell and found no other raw custom-tool name. The turn completed. No source media, project draft or user-host desktop was involved.

Earlier attempts remain failed evidence: a plain function definition led to a completed turn without a host call; a namespaced function reached the host but the first handler rejected it because `item/tool/call.params.tool` was the bare `editor_probe` name rather than the model-visible namespace-qualified name. A corrected namespaced call passed, followed by the stricter catalog, inventory and rollout-audited rerun. These observations apply to the tested turns only. They do not prove a complete upstream effective-tool allowlist, child inheritance, production project-thread resume, guarded draft dispatch, or a native Electron window. P2-07 and the full phase remain open.

The checked-in `tests/native/codex-dynamic-tools-probe.test.ts` requires an already authorized mode-600 guest-only credential profile and writes only bounded status and counts under ignored `test-results/`. It never reads or prints credential bytes. A future migration must preserve existing MCP-backed project threads, map the six owned dotted tool names to stable host-defined names, validate correlated requests before invoking the shared transaction service, and prove commit/Undo/reopen and source immutability in packaged Electron before changing product routing.

A second isolated check, `tests/native/codex-dynamic-tools-resume.test.ts`, closes the first App Server process after one completed host-tool call, launches a fresh process with the same private account and context, resumes the exact thread ID using the generated `thread/resume` request (which has no `dynamicTools` field), and completes a second turn that calls the same owned tool. Both calls were received by the bounded host callback, with zero foreign host requests. This is evidence that this specific dynamic-tool definition survived one process restart and thread resume; it does not establish compatibility with earlier MCP-backed threads, full history projection, or production safety.

The next internal boundary slice generated the pinned `DynamicToolCallParams` and `DynamicToolCallResponse` types and added an optional editor adapter. It derives six stable host names from the existing reviewed schemas, validates the exact namespace/name and bounded request, maps back to the same service names, and encodes only bounded JSON or fixed safe errors. The project-thread client accepts these calls only when an internal invoker is supplied and the active thread/turn ID is known and matches; a call with no validated turn identity fails closed. Stream/history projection allows only that configured namespace and names without raw arguments or results. Unit tests cover owned calls, stale/foreign/unknown-turn quarantine, schema parity, response bounds, and redaction. The packaged app does not supply the invoker or register dynamic tools; mixed-route product selection still needs native proof.

A new direct isolated 0.155.1 timing probe used the adapter's exact six-tool namespace and read-only `project_get_summary` decoder. One Luna/high turn returned its validated `turn/start` ID before the one owned host request arrived, and completed with one call, zero early/foreign/mismatched calls. Two retained failed setup runs used an older packaged binary without the matching code-mode host; each completed with no host request and cannot establish timing. The passing run used the matching native binary and host from the pinned guest package. This single observation narrows the race but does not remove the fail-closed early-call guard, establish all scheduling orders, migrate MCP-backed threads, or prove packaged Electron draft dispatch.

The registry migration slice persists `toolRoute` with each thread binding under schema version 2. Strict v1 entries decode as MCP and stay byte-for-byte untouched until another binding write. A new internal dynamic thread includes the exact six reviewed tool specs at start; resume uses its stored route and rejects a missing/mismatched boundary before RPC. Unit tests cover v1 migration, corrupt routes, dynamic resume and cross-route server-request rejection. The packaged main still selects MCP and has not exercised this route in a native edit.

The isolated packaged regression passed a real Luna/high MCP trim, same-thread reopen, Codex Undo and interruption, with guest-only native inspection. A separate synthetic v1 registry record for that real thread reopened and completed an owned read-only turn without rewriting the file. A later product-created thread migrated the registry to v2 and retained the old MCP ID, verified by private hash comparison. That second broad authenticated edit fixture failed after its correct trim at a post-turn assertion; retain it as a failed run rather than treating the whole fixture as passed. Product host-tool dispatch and effective confinement remain untested.

The later correlation slice addresses the `turn/start` response race without trusting a model-provided turn ID. While the RPC is pending, only a validated `turn/started` notification for the registry-owned thread may provisionally bind the turn; a subsequent `item/tool/call` must name that exact turn and the reviewed tool. A call before notification, after buffered completion, or with a conflicting response or remote rejection quarantines the client. Stream notifications remain buffered until response reconciliation, so the renderer still sees authoritative ordered state. The [official App Server contract](https://developers.openai.com/docs/app-server) describes the dynamic tool lifecycle but does not guarantee the relative arrival of a `turn/start` response and host request; that ordering concern is an inference from the separate RPC and notification channels. Focused tests simulate both orders and contradictions. A direct isolated official 0.155.1 `CodexClient` run without MCP completed one Luna/high owned summary read using the optional six-tool route. It did not establish whether that host call arrived early; it did not mutate a draft or launch packaged Electron. Product main still uses MCP, so mixed-route native editing and complete effective confinement remain open.
